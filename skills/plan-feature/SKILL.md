---
name: plan-feature
description: Plan a feature or step in plan mode with a workflow of read-only agents (scouts, domain planners, adversarial critics), then build it. Use when the user asks to plan a change across subsystems or with real risk, or to plan with a workflow, or runs /ccinformer:plan-feature.
argument-hint: <task to plan>
---

Plan: $ARGUMENTS

"You" below is the main session. The user doesn't read the scout, planner or critic output: you read it, check it, and bring the user only the decisions and a short account of what changed.

1. Plan mode must be on. If it isn't, stop and ask the user to switch to it. Workflow agents inherit plan mode, and that is what keeps them read-only. Plan mode's own Agent tool allows only 3 agents per phase, so the fan-out goes through the workflow below.
2. Scope inline first, just enough to name the domains:
   - the project CLAUDE.md and its **planning settings**: a committed Planning section (a `## Planning` heading in CLAUDE.md, or `.claude/planning.md`), then the private `.local/ccinformer-planning.md`, which adds to it or overrides it. They give the standing scouts, extra critic lenses, the project's checks (full, and scoped: fast checks on a few files), which actions need approval, the commit/PR/docs rules and where plans go. With neither, use the defaults here, and note what this run learns for step 9's finish;
   - the design and architecture docs (ADRs, module docs, specs): headings, then what the task touches;
   - the recent git log and the files the task touches; note the branch and `git rev-parse --short HEAD`, the commit this plan is made against (a repo with no commits yet: record "no commits yet" and the date instead), and which of the files the task touches are uncommitted (`git status --short`);
   - research already done in this session or written down (reports, plans, explorer results): this becomes `priorFindings`, so the scouts verify it instead of redoing it.
3. Write the **requirements** down before any agent runs, a few lines each:
   - the goal, and who it is for (users, roles);
   - the current behaviour and the desired one, with the edge and error cases;
   - measurable success criteria;
   - deadline and stakeholders;
   - what is out of scope, each with its reason.

   What the user hasn't confirmed is marked as open. A fact the code or docs can answer is looked up, never asked. A decision is a choice between workable options that changes what gets built or what users see. Ask now, before any agent runs, only a decision that changes which domains or agents the plan needs, and write its answer into the requirements; the rest wait for step 7.
4. Choose the agents:
   - **Step down:** if the task text doesn't ask for a workflow and the task plainly stays in one subsystem with no real risk (data migrations, access rules, a shared environment), ask with AskUserQuestion whether to switch to `/ccinformer:plan-feature-small`, and wait for the answer; on a yes, continue there with the same task.
   - Scouts: one per subsystem the task touches, plus the standing scouts from the planning settings. Add a scout only for ground no other scout covers. A scout can use another agent type (`agentType`), for example `claude-code-guide` for questions about Claude Code itself. One scout's brief also checks the task's premise: search for an existing implementation by concept, not only by the task's words, and note where you looked; a reported bug is confirmed (its code path), refuted or unclear.
   - Models: every workflow agent runs on Opus at high effort at most (the scripts cap it). By default scouts run on Sonnet at medium, planners and the fan-out's critics on Opus at high, the final check's critic on Opus at medium; the Agent settings (below) and the task text (`scouts on Opus`) change that, within the cap. Where the scouts have no setting, give a scout `model: 'opus', effort: 'high'` when the plan rests on its report unchecked: proving an absence, access rules, migration safety.
   - **Agent settings.** Once in this run, here and not earlier, read `~/.claude/ccinformer/skills.json` (under `$CLAUDE_CONFIG_DIR` when set). Its `agents` (script name: `plan-fanout`, `plan-review`, `build-fanout`; then role; then `model` and `effort`) is what the user set in Debug › Settings; start from it, or `{}`. Apply the task text's asks on top: a role (`critics on Sonnet`) in every script this run calls unless the ask names one (`final check on Sonnet`); one scout or package on that item's own `model`/`effort`. Don't raise, on your own, a single item whose role has a setting. Before the first Workflow call, tell the user in one line which roles change, "the rest on the scripts' defaults". Once the plan file exists, write `Agent settings for this run: <the object as JSON>` (`{}` when empty) into its Context. From then on that line is the source: every Workflow call of this run (a re-check, the final check, a resumed run, the build waves, also in a new context) passes `<object>["<script name>"]` as `agents`, left out when absent, never from a later read of the file. A line like it in prior findings, a handoff doc or another plan records that run only.
   - Planners: 1 to 3. Their domains don't overlap and together cover the whole task: every file belongs to exactly one planner, and each brief says which.
   - Critics: the workflow's defaults (correctness, fit, gaps), plus the planning settings' lenses as `extraCritics`, plus a lens for any concrete risk (security and access rules, data or migration safety, performance, i18n or design system).
   - At most 10 agents per phase (the script refuses more). Respect the session's workflow size guideline. Tell the user the counts in one line before starting.
5. Read this skill's `plan-fanout.js` (next to this file) and run the Workflow tool with its whole content as `script` (a `scriptPath` only works for files inside the working directory or an added directory, so passing it inline works from any project), and args:
   `{ context, requirements, priorFindings?, scouts: [{key, brief, agentType?, model?, effort?}], planners: [{key, brief}], critics?, extraCritics?: [{key, focus}], agents? }`.
   `agents` is `plan-fanout`'s entry in this run's agent settings (step 4), left out when it has none.
   `context` holds: a map of the project (paths), the task as decided so far, and rules specific to this task. Don't paste CLAUDE.md rules: the agents get CLAUDE.md themselves.
   If the result lists `missingPlanners`, the critique was skipped: re-run those planners before going on. If it lists `missingCritics`, those lenses gave nothing: run them as a re-check (`critics` set to them).
6. Check the review yourself. The critics return structured findings (severity, claim, evidence, file and line, minimal fix); a critique or final check marked `fallback` also has `unparsed` lines, findings as raw text to read like the rest. Don't trust them blindly:
   - check every blocker and should-fix against the code;
   - fold in the real ones and drop the wrong ones;
   - if a finding needs facts nobody gathered, run a small follow-up.

   If the fixes changed the plan substantially, run a re-check: the same script with `{ context, requirements, recheck: { plan, changes }, agents? }` (the same `agents` as the first run), critics only. Write the revised plan into the plan file first and pass its path as `plan` ("Read the full revised plan at <path>, then verify it against the code"): the critics read it themselves, so the plan isn't pasted into every prompt. What you change after the last review (this run, or the re-check) gets the final check in step 8.
7. Ask the real decisions with AskUserQuestion, the recommended option first. Ask in rounds: each round asks only the decisions whose prerequisites are settled (at most 4 per AskUserQuestion call); one that hangs on an open decision or a running lookup waits for the next round.
   - Decisions for other stakeholders (a repo owner, a team) go in the plan as a block the user can send: per stakeholder, most important first, one idea each, with your recommendation and the checkpoint it blocks (named after the question, never leading the line); don't ask the user to answer for them.
   - Take defaults for the rest and list them in the plan.
   - When an option adds scope, its description gives its size (small, medium, large, and why). Scope the user adds that no planner covered gets a **follow-up**: ask its own decisions first, then one Plan agent with the settled contract and only the new scope, then fold its plan in, check it against the code like a critic's finding, and run the re-check from step 6 over the whole plan.
8. Write the plan file, with:
   - **Context**: why, what was asked, the Base line (`Base: <branch> @ <commit>; uncommitted: <touched files, or none>`), "planned with a workflow of N agents", the `Agent settings for this run` line (step 4), each blocker and should-fix and how it was folded in (one line each, starting with its source: `[critic: <lens>]`, `[critic: final]` or `[main session]`), the final check's result (or "no final check: nothing changed"), and what changed after it without another review (read those parts hardest while building).
   - **Requirements and success criteria**, as confirmed.
   - **The user's decisions**, the defaults taken, and the open questions for stakeholders.
   - **The contract**: the exact public names and signatures, the data contract (columns, constraints, access rules, API or JSON shapes, storage paths) and the user-facing texts (UI strings) that cross between domains. The planners' versions always disagree somewhere, so settle each one once here. This is what you build against, so nothing gets re-decided mid-build.
   - **Checkpoints**, in build order, each with a measurable "done when". Define each where CCInformer's plan board (Work › Plans) finds it: its id at the start of a heading (`### CP1: title`), of a table row (`| CP1 | title | done when |`) or of a bold label (`- **CP1, title:**`), followed by punctuation. Ids look like `CP1`, `C1`, `R1` or `PR 1`. Its status goes on that same line, and nowhere else: nothing while open, `done` once its "done when" holds, `merged as #N` once its PR merges, `dropped` if abandoned. Each is a thin slice through every layer it touches, checkable on its own. A prefactor that makes the change easy comes first, as its own checkpoint; a bug fix's checkpoint starts by reproducing the user's exact symptom and seeing it fail (or says why no seam reaches it) and ends with the fix, so it ends green; a wide mechanical change goes as expand, migrate in batches, contract. Write each "done when" in the present tense, with no word the board reads as a status (done, passed, dropped, superseded, obsolete, partly) until it has that status. Checkpoint 0, the contract in code, counts as a prefactor.
   - **Work packages**, only when the build splits into 2 or more substantial pieces with separate files (else write "built in the main session"):
     - checkpoint 0 is the contract in code (shared types, signatures, stubs, keys and texts), built by you, so the project compiles before any package starts;
     - per package: a key, the files it owns (no file in two packages), the part of the contract it implements, its "done when", and its wave (a package that needs another's output goes in a later wave; at most 3 per wave; a wide change's batches map onto packages by directory);
     - the **reserved files**: every file more than one package needs (the planners list them: barrels, route tables, translation tables, config, shared types), plus lockfiles and generated code. You build these; packages only say what they need there.
   - **Approval gates**: every action that writes to a shared environment, a database, a service or git, marked "⚠ needs the user's OK", at the checkpoint where it happens.
   - **Rollout**: how it is deployed (CI, migration order, functions), what behaves differently after deploy, how it is rolled back. This feeds the PR description.
   - **Commits and PRs**: which checkpoints become which commits and PRs, following the repo's commit and PR rules. Commits only when the user asks.
   - **How it gets built** (step 9): you build it, in checkpoint order, or in waves of work packages; name any menial tasks that go to background agents.
   - **Verification**: the project's checks; the seams the tests go through (existing public interfaces, the highest that reaches each rule, never internals; a rule no seam reaches yet says so); the tests that encode the business and access rules, with expected values from a source independent of the code (a known literal, a worked example, the spec), and any test a deeper one replaces, named with its replacement; and a before/after measurement when the task is about performance.

   **Your own check.** With the answers in the plan file, check what no critic saw whole: intent (it does what the user asked and meant, honours their decisions, stays in scope) and the seams where the planners' drafts meet in the contract (names, shapes, texts, checkpoint order). Don't redo the critics' lenses. Fold in what you find, tagged `[main session]`; each is a change for the final check.

   **Final check.** If the plan changed since the last review, read `plan-review.js` (next to this file) and run it with the Workflow tool, its whole content as `script`, and args `{ context, requirements, plan, files, round: 'final', changes, lenses?, agents? }`: `agents` is `plan-review`'s entry in the plan's Agent settings line, `plan` the plan file's path, `files` the 1 to 30 files the changes touch, `lenses` at most 3 of your extra critics the changes touch (`{key, focus}`, a lowercase key of letters, digits and `-`, other than correctness, fit and gaps). A change is anything in the requirements, decisions, contract, checkpoints, approval gates or verification since the last review, not Context's account of it: the critics' findings folded in, a re-check's, the user's answers, a follow-up, your own check's findings, and the merge itself (the contract points settled between the planners; without a re-check the critics saw only the planners' plans, so list the plan file's sections as merged). List each in `changes`, one per line. Check its blockers and should-fixes against the code and fold in the real ones; no re-check follows it. If it returns an `error`, run it once more; if that fails too, say so in Context. Skip it when nothing changed. It runs at most once: what changes after it, or after a skipped one (such as feedback on ExitPlanMode), is named in Context as unreviewed.

   Before calling ExitPlanMode, read the plan file through once as its builder: every cross-reference (step numbers, checkpoint numbers, section names) points at the right place and no placeholder is left. Then call ExitPlanMode.
9. Once the plan is approved, build it. **You do the implementing yourself**, checkpoint by checkpoint, in the main session: the code, the tests and the docs. A builder agent is much slower, and you already hold the plan and the review. The exception is a plan with work packages (below).
   - **Plan files switch:** read `~/.claude/ccinformer/skills.json` (under `$CLAUDE_CONFIG_DIR` instead of `~/.claude` when that variable is set), for `planFiles` only: the agent settings stay as the plan's line has them. `"planFiles": false` means the user switched plan files off in CCInformer's Debug › Settings: skip the copy below and the planning-settings offer at the end, build from Claude Code's own plan file (the one you wrote in plan mode) and keep its checkpoint lines current there, and tell the user in one line that plan files are off, so Work › Plans won't show this plan. A missing file means on.
   - **Save the plan where the user can follow it:** copy the approved plan file to `.local/plans/<YYYY-MM-DD>-<slug>.md` from the project root (or the plans folder the planning settings name), where CCInformer's Work › Plans shows its checkpoints. From here on that copy is the plan you build from and keep current.
   - **`.local/` is written only where git ignores it:** before writing a file under the project's `.local/`, run `git check-ignore -q -- <its folder>/` from the project root (the folder with a trailing slash, for example `.local/plans/`). Exit 0 means git ignores it; anything else (1, or an error such as no git repo) means it doesn't, and nothing is written there. For the plan: when git doesn't ignore the plans folder under `.local/` (the default, or one the planning settings name), skip the copy, tell the user in one line that git doesn't ignore it and that adding `.local/` to `.gitignore` fixes it, and build from Claude Code's own plan file, keeping its checkpoint lines current there, as with plan files off. A plans folder the planning settings name outside `.local/` isn't under this rule: check it the same way, and if git doesn't ignore it, ask the user where to keep the plan instead, as it could otherwise get committed.
   - **Build rules:** read `build-rules.md` next to this file and follow it from here to the finish: the base check, checkpoint lines, build decisions, tests first, making checks pass, failing checks, quoting, what you find outside the task, approval gates, git, and the finish. If it can't be read, say so and stop before the first checkpoint.
   - **Order:** the plan's checkpoint order (the shared code the contract describes first, checkpoint 0 with work packages, then the slices), keeping everything compiling and the existing tests green.
   - **Work packages**, when the plan has them. All packages share this working tree; separate file lists and the reserved files are what keep them apart.
     - Build checkpoint 0 yourself and run the full checks once.
     - Per wave: snapshot the tree with `bash <this skill>/wave-snapshot.sh <scratch dir>/wave-<n>-before.txt` (bash: Git Bash on Windows) (read-only; hashes every file, so later changes are exact even in files that were already modified). Then read this skill's `build-fanout.js` and run the Workflow tool with its whole content as `script`, and args `{ context, plan: <plan file path>, wave, packages: [{key, brief, files, doneWhen, model?, effort?}], reserved, scopedChecks, snapshot: {script, baseline}, agents? }`. `agents` is `build-fanout`'s entry in the plan's Agent settings line, left out when it has none; a package gets its own `model`/`effort` only where the user asked for it or the builders have no setting. `context` is as in step 5; `scopedChecks` comes from the planning settings, or name the fastest checks that take file paths. Each package gets a builder, a read-only reviewer that checks it against the plan and git, and one fix round when the review asks for it.
     - While the wave runs, build the reserved files and what the packages will need there.
     - When it returns: for each package, read the review and check the fix yourself (the diff on its files, the scoped checks). Settle `blocked` and `escalated` packages yourself: decide, or ask the user if it's a real decision. Add what the packages listed under "needed in reserved". Run `bash <this skill>/wave-snapshot.sh --changed <baseline>`: a changed file outside every package's files and your reserved files is a stray; find out where it came from, and never revert a change you can't attribute.
     - Then run the full checks once for the wave, fix what they catch, and start the next wave.
   - **Agents only for menial or quick tasks** (outside work packages) that run in the background while you keep working: a mechanical rename across many files, a throwaway screenshot scene, a lookup. At most 10 at a time, each owning its files, so no file is held by two at once. Run them with `model: 'sonnet'` and `effort: 'medium'`; one that needs judgment gets `model: 'opus'` and `effort: 'high'`, never more (the same cap as the workflows' agents).
   - **Each agent brief gives:**
     - the plan path and the section the agent owns;
     - the files it owns, and that it must not touch others;
     - "read the actual code, not this summary";
     - if the contract or API lacks something, stop and report rather than edit outside its files;
     - the project's checks to run, and that it never loosens, skips or deletes a test or check to make it pass (a check that looks wrong is reported, not changed);
     - git is read-only: no commit, push, stash, checkout, restore, reset, clean or branch switch, since the working tree holds other uncommitted work that these would roll back;
     - anything it notices outside its task goes under "Found outside the task" in the report, one line each (`path: what`), not fixed;
     - command output quoted sparingly: only the lines that carry the signal, with `<REDACTED>` for a secret;
     - a short report with a word limit, covering deviations from the contract, the exact texts, and the files it changed.
   - **Check each agent against git, not its report:** before it starts, note `git status --short`; when it returns, run `git status --short` and `git diff` on its files. A file it reports as changed that git shows unchanged, a change outside its files that neither you nor another agent made, or a weakened test sends the work back with the reason.
   - **Finish:** as the build rules say.
