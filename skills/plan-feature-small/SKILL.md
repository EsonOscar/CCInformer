description: Light planning in plan mode with no review agent, then the build. You scout, plan and review the plan yourself against the code, lens by lens. Use when the user asks for a quick or light plan, or runs /ccinformer:plan-feature-small; for a large or risky change, offer /ccinformer:plan-feature.
argument-hint: <task to plan>

Plan (small): $ARGUMENTS

"You" below is the main session: you scout, plan and review the plan yourself, with no review agent, so it stays fast and costs a fraction of the tokens. If the task spans several subsystems or carries real risk (data migrations, access rules, a shared environment), ask with AskUserQuestion whether to switch to `/ccinformer:plan-feature-medium` (two critic agents review the plan) or `/ccinformer:plan-feature` (a full workflow of agents), and wait for the answer; on a choice, continue there with the same task.

1. Plan mode must be on. If it isn't, stop and ask the user to switch to it (Shift+Tab until the bottom of the screen says plan mode), then run the command again.
2. Read what the task needs, and only that:
   - the project CLAUDE.md and its **planning settings**: a committed Planning section (a `## Planning` heading in CLAUDE.md, or `.claude/planning.md`), then the private `.local/ccinformer-planning.md`, which adds to it or overrides it. They give the project's checks, the extra critic lenses, which actions need approval, the commit, PR and docs rules, and where plans go. With neither, use the defaults here, and note what this run learns for step 8's finish;
   - the files the task touches, and the code they call or are called by, read in full where a decision rests on them;
   - the recent git log on those files; note the branch and `git rev-parse --short HEAD`, the commit this plan is made against (a repo with no commits yet: record "no commits yet" and the date instead), and which of the files the task touches are uncommitted (`git status --short`);
   - **the premise:** search for an existing implementation by concept, not only by the task's words, and note where you looked; a reported bug is confirmed (its code path), refuted or unclear.

   For ground too big to read in one go, you may run **at most two** Explore agents (`model: 'sonnet'`, read-only), each with one narrow question and a word limit. Check anything you build on against the code yourself. Done when every file the task changes, and each caller a decision rests on, is opened and listed: your review opens them again.
3. Write the **requirements** down, a few lines each: the goal and who it is for, the current behaviour and the desired one, with the edge and error cases, measurable success criteria, and what is out of scope, each with its reason. What the user hasn't confirmed is marked as open. A fact the code or docs can answer is looked up, never asked. A decision is a choice between workable options that changes what gets built or what users see.
4. Draft the whole plan into the plan file, so the review is of the real plan:
   - **Context**: why, what was asked, the Base line (`Base: <branch> @ <commit>; uncommitted: <touched files, or none>`), and how it was reviewed with what the review changed (filled in at step 7).
   - **Requirements and success criteria.**
   - **Decisions**: the user's, and the defaults taken.
   - **The contract**: the exact public names and signatures, the data shapes and the user-facing texts the change adds or changes.
   - **Checkpoints**, in build order, each with a measurable "done when". Define each where CCInformer's plan board (Work › Plans) finds it: its id at the start of a heading (`### CP1: title`), of a table row (`| CP1 | title | done when |`) or of a bold label (`- **CP1, title:**`), followed by punctuation. Ids look like `CP1`, `C1`, `R1` or `PR 1`. Its status goes on that same line, and nowhere else: nothing while open, `done` once its "done when" holds, `merged as #N` once its PR merges, `dropped` if abandoned. Each is a thin slice through every layer it touches, checkable on its own. A prefactor that makes the change easy comes first, as its own checkpoint; a bug fix's checkpoint starts by reproducing the user's exact symptom and seeing it fail (or says why no seam reaches it) and ends with the fix, so it ends green; a wide mechanical change goes as expand, migrate in batches, contract. Write each "done when" in the present tense, with no word the board reads as a status (done, passed, dropped, superseded, obsolete, partly) until it has that status.
   - **Approval gates**: every action that writes to a shared environment, a database, a service or git, marked "⚠ needs the user's OK", at the checkpoint where it happens.
   - **Verification**: the project's checks; the seams the tests go through (existing public interfaces, the highest that reaches each rule, never internals; a rule no seam reaches yet says so); the tests that encode the business and access rules, with expected values from a source independent of the code (a known literal, a worked example, the spec), and any test a deeper one replaces, named with its replacement.
5. **Review the plan yourself.** No agent reviews this plan, so this step is the only review it gets. Do it as its adversary, not its author: assume the plan is wrong until the code says otherwise.
   - **Against the code, not from memory.** Open the files the plan touches again and check every name, signature, data shape, text and behaviour the plan relies on where it is defined. Something the plan relies on that you can't find in the code is a finding.
   - **Through each lens in turn**, noting the files you opened for each:
     - `intent`: it does what the user asked and meant, honours their decisions (asked at step 6, checked at step 7), stays in scope;
     - `correctness`: correctness against the actual code (verify every signature and behaviour the plan assumes by reading it), edge cases, tests or invariants that could pass wrongly (an expected value worked out the way the code works it out, a test that reaches past the public interface), YAGNI;
     - `fit`: whether the plan agrees with the existing code and the project rules (naming, structure, the docs that must change), every mismatch in the shapes and names it uses, and a new module or seam that does not earn its place (deleting it would move no complexity into its callers; nothing varies across it, not even a test stand-in);
     - `gaps`: what the plan leaves out from the requirements and the task, a requirement or premise the code contradicts (quote both), a bug fix whose checkpoint does not start by reproducing the symptom, with no stated reason none can, contradictions inside it, checkpoints that cannot be measured, and whether everything still builds and passes after each checkpoint;
     - then each of the planning settings' extra critic lenses.
   - **Each finding** is a blocker (would break, contradict the code or the requirements, or skip a needed approval), a should-fix or a nit, with its file and line where there is one. Fold the real ones into the plan file, and keep one line on each blocker and should-fix for Context, starting `[main session]`.
   - **Rounds.** Go again after a round that found a blocker or changed the contract, a checkpoint or a "done when", checking those changes hardest and whether a fix broke something else. Stop after a round with no blocker and no such change; three rounds at most, and what is still open after the third is listed in the plan as open.

   If the review shows the task is larger or riskier than it looked, ask the same; on a choice, continue in that skill with this plan file as its prior findings.
6. Ask the real decisions with AskUserQuestion, the recommended option first; take defaults for the rest and list them in the plan. Ask in rounds: each round asks only the decisions whose prerequisites are settled (at most 4 per AskUserQuestion call); one that hangs on an open decision or a running lookup waits for the next round. When an option adds scope, its description gives its size (small, medium, large, and why).
7. Finish the plan file:
   - **Check every late change.** A change after your last round (an answer, a fix) is checked the same way: against the code, against intent, and for a broken cross-reference, checkpoint or "done when". Go again while a check changes something, twice at most; name what is left, and anything after it (such as feedback on ExitPlanMode), in Context as unreviewed.
   - In Context: "reviewed by the main session, N rounds; no agent reviewed it", the files each lens opened in the last round, each blocker and should-fix in one line starting `[main session]`, with what changed, and every change made after the last check, unreviewed.
   - Read it through once as its builder (cross-references right, no placeholder left), then call ExitPlanMode.
8. Once the plan is approved, build it yourself, checkpoint by checkpoint, in the main session: the code, the tests and the docs.
   - **Plan files switch:** read `~/.claude/ccinformer/skills.json` (under `$CLAUDE_CONFIG_DIR` instead of `~/.claude` when that variable is set), for `planFiles` only. `"planFiles": false` means the user switched plan files off in CCInformer's Debug › Settings: skip the copy below and the planning-settings offer at the end, build from Claude Code's own plan file (the one you wrote in plan mode) and keep its checkpoint lines current there, and tell the user in one line that plan files are off, so Work › Plans won't show this plan. A missing file means on.
   - **Save the plan where the user can follow it:** copy the approved plan file to `.local/plans/<YYYY-MM-DD>-<slug>.md` from the project root (or the plans folder the planning settings name), where CCInformer's Work › Plans shows its checkpoints. From here on that copy is the plan you build from.
   - **`.local/` is written only where git ignores it:** before writing a file under the project's `.local/`, run `git check-ignore -q -- <its folder>/` from the project root (the folder with a trailing slash, for example `.local/plans/`). Exit 0 means git ignores it; anything else (1, or an error such as no git repo) means it doesn't, and nothing is written there. For the plan: when git doesn't ignore the plans folder under `.local/` (the default, or one the planning settings name), skip the copy, tell the user in one line that git doesn't ignore it and that adding `.local/` to `.gitignore` fixes it, and build from Claude Code's own plan file, keeping its checkpoint lines current there, as with plan files off. A plans folder the planning settings name outside `.local/` isn't under this rule: check it the same way, and if git doesn't ignore it, ask the user where to keep the plan instead, as it could otherwise get committed.
   - **Build rules:** read `build-rules.md` in the plan-feature skill's folder (`../plan-feature/build-rules.md` from this file) and follow it from here to the finish: the base check, checkpoint lines, build decisions, tests first, making checks pass, failing checks, quoting, what you find outside the task, approval gates, git, and the finish. If it can't be read, say so and stop before the first checkpoint.
   - Order: build checkpoint by checkpoint, keeping everything compiling and the existing tests green.
