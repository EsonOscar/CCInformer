---
name: plan-handoff
description: Multi-agent planning for someone who isn't a developer, ending in a handoff doc instead of a build. Same fan-out as plan-feature (read-only scouts, 1 to 3 domain planners, adversarial critics, every finding checked against the code), with the user asked only product decisions in plain words, technical choices left for the developer, and the approved plan written as a .md file a developer builds from, closing with how it was planned. Use when the user wants a feature planned for a developer to build later, or runs /ccinformer:plan-handoff.
argument-hint: <feature to plan>
---

Plan for a developer: $ARGUMENTS

"You" below is the main session. The **user** is not a developer: they know what the feature should do and who it is for, not how the code works. The **developer** builds it later, in a new session, from the doc this skill writes. The user doesn't read the scout, planner or critic output: you read it, check it, and bring the user only the product decisions, in plain words.

1. Plan mode must be on. If it isn't, stop and ask the user to switch to it: press Shift+Tab until the bottom of the screen says plan mode, then run the command again. Workflow agents inherit plan mode, and that is what keeps them read-only.
2. Scope inline first, just enough to name the domains:
   - the project CLAUDE.md and its **planning settings**: a committed Planning section (a `## Planning` heading in CLAUDE.md, or `.claude/planning.md`), then the private `.local/ccinformer-planning.md`, which adds to it or overrides it. They give the standing scouts, extra critic lenses, the project's checks, which actions need approval, the docs rules and where plans and handoff docs go. With neither, use the defaults here, and note what this run learns for step 9;
   - the design and architecture docs (ADRs, module docs, specs): headings, then what the task touches;
   - the recent git log and the files the task touches; note the branch and `git rev-parse --short HEAD`, the commit this plan is made against (a repo with no commits yet: record "no commits yet" and the date instead), and which of the files the task touches are uncommitted (`git status --short`);
   - research already done in this session or written down: this becomes `priorFindings`, so the scouts verify it instead of redoing it.
3. Write the **requirements** down before any agent runs, a few lines each. The user is the source here: ask them in plain words for what is missing.
   - the goal, and who it is for (users, roles);
   - the current behaviour and the desired one, with the edge and error cases;
   - measurable success criteria (what a user can do afterwards that they can't now);
   - deadline and stakeholders;
   - what is out of scope, each with its reason.

   What the user hasn't confirmed is marked as open. A fact the code or docs can answer is looked up, never asked. A decision is a choice between workable options that changes what gets built or what users see.
4. Choose the agents:
   - Scouts: one per subsystem the task touches, plus the standing scouts from the planning settings. Add a scout only for ground no other scout covers. A scout can use another agent type (`agentType`). One scout's brief also checks the task's premise: search for an existing implementation by concept, not only by the task's words, and note where you looked; a reported bug is confirmed (its code path), refuted or unclear.
   - Models: every workflow agent runs on Opus at high effort at most (the scripts cap it). By default scouts run on Sonnet at medium, planners and the fan-out's critics on Opus at high, the final check's critic on Opus at medium; the Agent settings (below) and the task text (`scouts on Opus`) change that, within the cap. Where the scouts have no setting, give a scout `model: 'opus', effort: 'high'` when the plan rests on its report unchecked: proving an absence, access rules, migration safety.
   - **Agent settings.** Once in this run, here and not earlier, read `~/.claude/ccinformer/skills.json` (under `$CLAUDE_CONFIG_DIR` when set). Its `agents` (script name: `plan-fanout`, `plan-review`; then role; then `model` and `effort`) is what the user set in Debug › Settings; start from it, or `{}`. Apply the task text's asks on top: a role (`critics on Sonnet`) in every script this run calls unless the ask names one (`final check on Sonnet`); one scout on its own `model`/`effort`. Don't raise, on your own, a single item whose role has a setting. Before the first Workflow call, tell the user in one line which roles change, "the rest on the scripts' defaults". Once the plan file exists, write `Agent settings for this run: <the object as JSON>` (`{}` when empty) into its Context. From then on that line is the source: every Workflow call of this run (a re-check, the final check, a resumed run, also in a new context) passes `<object>["<script name>"]` as `agents`, left out when absent, never from a later read of the file. A line like it in prior findings, a handoff doc or another plan records that run only.
   - Planners: 1 to 3. Their domains don't overlap and together cover the whole task: every file belongs to exactly one planner, and each brief says which.
   - Critics: the workflow's defaults (correctness, fit, gaps), plus the planning settings' lenses as `extraCritics`, plus a lens for any concrete risk (security and access rules, data or migration safety, performance, i18n or design system).
   - At most 10 agents per phase (the script refuses more). Respect the session's workflow size guideline. Tell the user the counts in one plain line before starting.
5. Read `plan-fanout.js` from the plan-feature skill's folder (`../plan-feature/plan-fanout.js` from this file; both skills share it) and run the Workflow tool with its whole content as `script` (a `scriptPath` only works for files inside the working directory or an added directory, so passing it inline works from any project), and args:
   `{ context, requirements, priorFindings?, scouts: [{key, brief, agentType?, model?, effort?}], planners: [{key, brief}], critics?, extraCritics?: [{key, focus}], agents? }`.
   `agents` is `plan-fanout`'s entry in this run's agent settings (step 4), left out when it has none.
   `context` holds: a map of the project (paths), the task as decided so far, rules specific to this task, and this audience rule, verbatim: "The person planning is not a developer. Under 'for the user', ask only product questions (what it does, for whom, the wording users see, what users see in edge cases), in plain words. Put technical choices under 'for other stakeholders' as questions for the developer, each with your recommendation." Don't paste CLAUDE.md rules: the agents get CLAUDE.md themselves.
   If the result lists `missingPlanners`, the critique was skipped: re-run those planners before going on. If it lists `missingCritics`, those lenses gave nothing: run them as a re-check (`critics` set to them).
6. Check the review yourself. The critics return structured findings (severity, claim, evidence, file and line, minimal fix); a critique or final check marked `fallback` also has `unparsed` lines, findings as raw text to read like the rest. Don't trust them blindly:
   - check every blocker and should-fix against the code;
   - fold in the real ones and drop the wrong ones, keeping a one-line reason for each dropped one;
   - if a finding needs facts nobody gathered, run a small follow-up.

   If the fixes changed the plan substantially, run a re-check: the same script with `{ context, requirements, recheck: { plan, changes }, agents? }` (the same `agents` as the first run), critics only. Write the revised plan into the plan file first and pass its path as `plan` ("Read the full revised plan at <path>, then verify it against the code"): the critics read it themselves, so the plan isn't pasted into every prompt. What you change after the last review gets the final check in step 8; only what changes after that goes under "Not re-reviewed" in the doc's last section. Keep the tally for that section too.
7. Ask the user the **product decisions** with AskUserQuestion: what the feature does, for whom, the wording users see, what users see in edge cases. Ask in rounds: each round asks only the decisions whose prerequisites are settled (at most 4 per AskUserQuestion call); one that hangs on an open decision or a running lookup waits for the next round. Plain words, no file names or code terms; the recommended option first; each option's description says what it means for the people using the feature.
   - Technical choices (data model, structure, libraries, migrations): take the recommended option and mark it "dev to confirm" in the doc.
   - Decisions for other stakeholders (a repo owner, a team) go in the doc as a block the user can send: per stakeholder, most important first, one idea each, with your recommendation and the checkpoint it blocks (named after the question, never leading the line); don't ask the user to answer for them.
   - When an option adds scope, its description gives its size in plain words (small, medium, large, and why). Scope the user adds that no planner covered gets a **follow-up**: ask its own product questions first, then one Plan agent with the settled contract and only the new scope, then fold its plan in, check it against the code like a critic's finding, and run the re-check from step 6 over the whole plan.
8. Write the handoff into the plan file, with:
   - **Summary**, for the user, in plain words, about five lines: what gets built, for whom, what changes for them. This is the part the user approves.
   - **Context**: why, what was asked, the `Agent settings for this run` line (step 4), and each blocker and should-fix and how it was folded in (one line each, starting with its source: `[critic: <lens>]`, `[critic: final]` or `[main session]`).
   - **Requirements and success criteria**, as confirmed.
   - **Decisions**: the user's product decisions; the technical defaults, each marked "dev to confirm"; the open questions for the developer and other stakeholders.
   - **The contract**: the exact public names and signatures, the data contract (columns, constraints, access rules, API or JSON shapes, storage paths) and the user-facing texts (UI strings) that cross between domains. The planners' versions always disagree somewhere, so settle each one once here, so the developer builds against it instead of re-deciding it.
   - **Checkpoints**, in build order, each with a measurable "done when". Define each where CCInformer's plan board (Work › Plans) finds it: its id at the start of a heading (`### CP1: title`), of a table row (`| CP1 | title | done when |`) or of a bold label (`- **CP1, title:**`), followed by punctuation, with nothing after it while it's open; the developer marks it on that same line (`done`, `merged as #N`, `dropped`). Each is a thin slice through every layer it touches, checkable on its own. A prefactor that makes the change easy comes first, as its own checkpoint; a bug fix's checkpoint starts by reproducing the user's exact symptom and seeing it fail (or says why no seam reaches it) and ends with the fix, so it ends green; a wide mechanical change goes as expand, migrate in batches, contract. Write each "done when" in the present tense, with no word the board reads as a status (done, passed, dropped, superseded, obsolete, partly) until it has that status. Checkpoint 0, the contract in code, counts as a prefactor. Close the section with these lines, verbatim: "For commit and PR styles, refer to repo guidelines." and "While building: make checks pass by fixing the code, never by loosening, skipping or deleting a test or check (a wrong check is flagged as its own change); each rule's test is seen failing before its code; decisions made while building go into this doc under a `## Build decisions` heading, as `Decision (<checkpoint id>): what and why`, never starting the line with the id; anything noticed outside this plan goes in a 'Found outside the plan' list for the PR, not fixed in passing; any agents helping get git read-only (no commit, push, stash, checkout, restore, reset, clean or branch switch), and their reported changes are checked against `git status` and `git diff`, not taken on trust."
   - **Work packages**, only when the build splits into 2 or more substantial pieces with separate files (else leave the section out): checkpoint 0 is the contract in code (shared types, signatures, stubs, keys and texts), so the project compiles before any package starts; per package a key, the files it owns (no file in two packages), the part of the contract it implements, its "done when", and its wave (a package that needs another's output goes in a later wave); and the reserved files every package may need (barrels, route tables, translation tables, config, shared types, lockfiles, generated code), which the developer builds themselves. The packages can be built one by one or in parallel, for example with /ccinformer:plan-feature's build waves.
   - **Approval gates**: every action that writes to a shared environment, a database, a service or git, marked "⚠ needs approval", at the checkpoint where it happens.
   - **Rollout**: how it is deployed (CI, migration order, functions), what behaves differently after deploy, how it is rolled back.
   - **Verification**: the project's checks; the seams the tests go through (existing public interfaces, the highest that reaches each rule, never internals; a rule no seam reaches yet says so); the tests that encode the business and access rules, with expected values from a source independent of the code (a known literal, a worked example, the spec), and any test a deeper one replaces, named with its replacement; the manual test steps the user can run to accept the feature; and a before/after measurement when the task is about performance.
   - **How this was planned**, last and tiny, at most about 10 lines:
     - "Planned with /ccinformer:plan-handoff (the planning half of /ccinformer:plan-feature) on <date>, against <branch> @ <commit>; uncommitted: <touched files, or none>."
     - Agents, one line: "Scout N (keys) · Plan N (domains) · Critique N (lenses)", plus follow-ups, re-checks and a final check if any ran; agent types only where not the default; then what the agents ran on, from each run's `ranOn` ("scouts sonnet/medium, planners and critics opus/high").
     - Review, one line: findings checked, folded in, dropped, and "final check: N findings, M folded in" (or "no final check: nothing changed"); then one short line per dropped blocker or should-fix saying why, so the building session doesn't raise it again.
     - Notes for the building session, at most four short lines: what was read in the code and what is assumed; anything under "Not re-reviewed" (step 8's final check); the "dev to confirm" items to settle first and the files to read first; check `git log <commit>..HEAD` on the touched paths for drift, and read any file listed as uncommitted first, then build checkpoint by checkpoint, or start with /ccinformer:plan-feature, passing this doc as the prior findings.

   **Your own check.** With the answers in the plan file, check what no critic saw whole: intent (it does what the user asked and meant, honours their decisions, stays in scope) and the seams where the planners' drafts meet in the contract (names, shapes, texts, checkpoint order). Don't redo the critics' lenses. Fold in what you find, tagged `[main session]`; each is a change for the final check.

   **Final check.** If the plan changed since the last review, read `plan-review.js` from the plan-feature skill's folder (`../plan-feature/plan-review.js` from this file) and run it with the Workflow tool, its whole content as `script`, and args `{ context, requirements, plan, files, round: 'final', changes, lenses?, agents? }`: `agents` is `plan-review`'s entry in the plan's Agent settings line, `plan` the plan file's path, `files` the 1 to 30 files the changes touch, `lenses` at most 3 of your extra critics the changes touch (`{key, focus}`, a lowercase key of letters, digits and `-`, other than correctness, fit and gaps). A change is anything in the requirements, decisions, contract, checkpoints, approval gates or verification since the last review, not Context's account of it: the critics' findings folded in, a re-check's, the user's answers, a follow-up, your own check's findings, and the merge itself (the contract points settled between the planners; without a re-check the critics saw only the planners' plans, so list the plan file's sections as merged). List each in `changes`, one per line. Check its blockers and should-fixes against the code and fold in the real ones; no re-check follows it. If it returns an `error`, run it once more; if that fails too, say so in the doc's last section. Skip it when nothing changed. It runs at most once: what changes after it, or after a skipped one (such as feedback on ExitPlanMode), is named under "Not re-reviewed".

   Before calling ExitPlanMode, read the plan file through once as the developer would: every cross-reference (step numbers, checkpoint numbers, section names) points at the right place, no placeholder is left (the closing line's template aside), the Summary matches the decisions, and quoted output is cut to its signal lines, with `<REDACTED>` for a secret. Then call ExitPlanMode.
9. Once the user approves, write the doc and finish. The build belongs to the developer's session, so your work ends with the file.
   - Path: the handoff folder the planning settings name, else `docs/plans/<YYYY-MM-DD>-<feature-slug>.md` from the project root. Look before overwriting an existing file.
   - **`.local/` is written only where git ignores it:** before writing a file under the project's `.local/`, run `git check-ignore -q -- <its folder>/` from the project root (the folder with a trailing slash, for example `.local/plans/`). Exit 0 means git ignores it; anything else (1, or an error such as no git repo) means it doesn't, and nothing is written there. A handoff folder under `.local/` that git doesn't ignore: ask the user where to put the doc instead. `docs/plans/` and any other folder outside `.local/` is written as named.
   - Content: the approved plan file, unchanged except that the `Agent settings for this run` line is left out of Context: it was this run's working note, and "How this was planned" already says what the agents ran on.
   - Git stays with the user: leave the file uncommitted.
   - Tell the user the path, what's in the doc in two lines, and that it is ready to send to the developer.
   - If the project had no planning settings, offer once to save what this run learned as `.local/ccinformer-planning.md` (only if git ignores `.local/`, by the rule above), unless `~/.claude/ccinformer/skills.json` (under `$CLAUDE_CONFIG_DIR` when set; read here for `planFiles` only) holds `"planFiles": false`, the user's Plan files switch in CCInformer's Debug › Settings; the handoff doc above is written either way: copy `planning-template.md` from the plan-feature skill's folder (`../plan-feature/` from this file), fill each section from the run (the project's checks, the scouts you used, the approvals the plan needs), mark anything you guessed "(check)", and leave a section you know nothing about as its placeholder.
